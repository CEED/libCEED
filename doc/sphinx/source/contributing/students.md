# Student Contributions

libCEED explicitly welcomes student contributions.
Students at University Colorado Boulder, San Diego State University, and other institutions have made contributions to libCEED, as part of course projects or independently.
We have a lot of experience guiding students through their first open source contributions.

Students looking to contribute to libCEED should follow these steps:

1) Read the [Introduction](../intro) and [Getting Started](../gettingstarted) pages to get a sense of what libCEED does.

2) Read the [GitHub Issues](https://github.com/CEED/libCEED/issues) to see what open tasks need help.
Tasks labeled with `student contribution` are particularly good options, but feel free to select any issue that looks interesting to you or suggest your own.

3) Comment on the issue (or create a new issue) detailing what work you would like to do.
It is perfectly fine if you don't quite know all of the right technical jargon for this post - this experience is all about learning and improving libCEED.
As a result, don't worry about using an LLM to 'polish' or 'improve' your writing.
Academia is an inherently multilingual endeavor and the libCEED team is experienced working with individuals who have different language backgrounds.
The most important thing in this step is to build understanding about what you would like to implement and for the core libCEED maintainers to provide advice to help you avoid potential problems or pitfalls.

4) Create a working branch on your fork of libCEED and start creating your changes.
If you get stuck or have questions, please reach back out on the issue for your task.
It is perfectly normal for development work to uncover new questions or decisions about the task.
You may use LLMs during this process (certainly is not required to do so), but please read and follow libCEED's [Contributing Guidelines](../CONTRIBUTING).
It is important to fully understand and assume responsibility for all code you submit, especially if the code was created with an LLM.

5) Create a [Pull Request](https://github.com/CEED/libCEED/pulls) from your fork to the main libCEED repo when you are ready.
All review discussions need to be conducted human-to-human with no LLMs.
Again, it is perfectly OK if you don't know all of the technical jargon or English is not your first language.
libCEED maintainers have a lot of experience with a lot of different contributors.
Maintainers asking a lot of questions and suggesting changes is totally normal, even for experienced contributors.
The Pull Request (PR) review process is for making sure all of us humans agree that the design is the right one for the task and the code is the best reflection of the design.

6) Once we're all happy with the code in the branch, we'll merge the code.
You'll have made a contribution to help us do real science on real supercomputers!

At the end of the day, our goals are to

- gain a new contribution that helps libCEED do better science

- help students learn about professional open source software development

Please reach out to us and let us help you contribute!
